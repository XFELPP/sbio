`sbio`'s modular and composable APIs afford uses a lot of power and flexlibility. It can, however, be a bit difficult to decide at first what approach to use, given the large number of choices available. To that end, the APIs are designed in a tiered fashion. Both in C++ and Python, a more limited set of initial constructs can be used before needing to dive into the full details and intricacies of all the underlying architecture. Limited in this case refers only to restrictions on the customizability - using the strategies below are no less powerful than building from scratch with the basic building blocks. In many cases, these will cover all the necessities.

To start out, the core objects to be aware of are the `DataSource` and the `BrokerGroup`. The `DataSource` can be used directly, however, it is recommended that a third `Context` object be used instead. This gives you a known working starting point - it ensures that your combinations of policies are valid, that they will run in the current process' environment, and will assist in any idiosyncrasies related to finding and data with the `DataSource`.

Beginning with the `Context`, we create a `DataSource`. In turn, the `DataSource` will be used to spawn `BrokerGroups`: These are the logical units of interest for accessing data. They represent a complete unit at a high level - e.g., an area detector.

Given a `DataSource` (spwaned by our `Context`) and our `BrokerGroup` we can then proceed through the iteration process. The `DataSource` generates `step`s. These are used by the `BrokerGroup` to access specific fields. Using just these two objects 90% of the use case is covered. You can later proceed into the internals for managing `StreamBroker`s directly, for example. Alternatively, see below on some of the more advanced iteration and event building utilities that are provided.

## `C++`

In C++, the `Context` is created with template parameters for selecting an IO strategy, and an Execution policy (which determines parallelization, synchronization and memory management). The data format itself is selected afterwards.

The `Context` is a global singleton - there is only, and can only ever be, one instance in the process (per selected IO/Execution combination).

Beginning with the `Context`, the process would then involve selecting the creation of a `DataSource` for the requested data format, perhaps after modifying any required environment variables. From there, the `BrokerGroup` can be created, and the `DataSource` iterated.

Each data format has a number of configuration paramters - this varies depending on the specific format. In general, though, the simplest workflow could be:

<Steps>

1. Create a `Context`. (And manage environment as necessary).
2. Create a `DataSource`.
3. Setup the configuration objects for the `DataSource`.
4. Run the load routine.
5. Create a `BrokerGroup`
6. Iterate until receiving an `ExhaustedSentinel`.

</Steps>


```cpp
#include <sbio/core/context.hh>             // Will create a Context
#include <sbio/core/datasource.hh>          // Will create a DataSource
#include <sbio/execution/mpi.hh>            // Will use an MPI execution policy
#include <sbio/formats/xtc2/xtc2_traits.hh> // Will read XTC2 data
#include <sbio/io/posix.hh>                 // Will read using POSIX APIs to start

#include <stdexcept>
#include <string>

// For simplicity, we will expose the `sbio` namespace. Nearly everything of
// interest is at the top-level `sbio::` namespace.

// Will create a Context to manage IO with POSIX APIs, using MPI.
// The Execution policy can be configured at this point.
sbio::MPIExecution::Config ecfg;
ecfg.main_rank = 0;          ///< The indexing rank is rank 0
ecfg.main_rank_loops = true; ///< Our indexing rank participates in iteration.
sbio::Context<sbio::SyncPOSIXIO, sbio::MPIExecution> ctx(ecfg);

// Double check all is well in the setup so far.
if (!ctx.ok()) {
  throw std::runtime_error("The Context encountered errors: " + ctx.error());
}

// Can query and set environment:
if (ctx.has_env("BAD_MODE")) {
  throw std::runtime_error("BAD_MODE mode unsupported!");
}

// Construct our DataSource for XTC2 now.
// Will be of type:
//
// using MPIDataSource = sbio::DataSource<
//   sbio::SyncPOSIXIO,
//   sbio::MPIExecution,
//   sbio::XTC2Traits
// >;
auto ds = ctx.data_source<sbio::XTC2Traits>();

// Setup options for the reading - there is generic configuration always applicable
// Then each data format may have a few additional fields particular to it.
sbio::GenericStreamConfig<sbio::XTC2Traits> base_cfg;
base_cfg.index_batch_size = 43200;    ///< How many step offsets will be read each time.
base_cfg.max_buffer_size = 0x4000000; ///< The maximum buffer size to read data into.

// In general, the above is all you need to start.

// Now, we load data. Each data format has a default Locator. We can also manually
// specify which to use.

std::string experiment { "abcd" };
unsigned run_num { 1234 };
bool found = ds.load_source(base_cfg, experiment, run_num); // For XTC2 the default is PathPattern.

// Or look for 1 file.
// ds.load_source_with<sbio::SingleFileLocator>(base_cfg, file_path);

if (!found) {
  throw std::runtime_error("No data found for " + experiment + " run " + std::to_string(run_num));
}

// Do initial discovery now.
auto status = ds.discover_metadata();
if (status != IOStatus::Success) {
  throw std::runtime_error("Error reading the data!");
}

// Finally, get a BrokerGroup and away we go!
auto grp = ds.get_stream_group("MyDetectorName");

// Use the simplest range iteration - 1 step at a time
for (auto step : ds.steps()) {
  // Pass the step, and the data request
  // Use the provided literals - order doesn't matter then.
  using namespace sbio::literals;

  auto data = grp.get_data(step, "raw"_alg, "raw"_field); // For XTC1 or CXI just pass field.
}
```

There is also the ability to pass in callbacks to be run automatically for each data fetch. NOTE: A single `BrokerGroup` may manage multiple "segment" references. I.e., the callback may run multiple times for each `step`! This should be kept in mind when designing one.

```cpp
  // ds, grp etc from before
  // All formats, IO policies, Execution policies, etc return sbio::DataResult
  auto cb = [&](sbio::DataResult res) {
    std::cout << "Processing...." << std::endl;
  };

  for (auto step : ds.steps()) {
    auto data = grp_get_data(step, cb, "raw"_alg, "raw"_field);
  }
```

## Python

For the Python side, the APIs have been split into 3 tiers from simplest to most configurable.

<Steps>

1. **Tier 1**: A single variant-based wrapper for the `DataSource` and `BrokerGroup`. Configuration is done via keyword arguments passed to the `DataSource` initializer to select which of the template variants is desired.
2. **Tier 2**: Bindings are provided for each of the concrete specializations that are supported. This API most closely mirrors the C++ API example above. You instantitate a specific fully-templated `DataSource` and go from there.
3. **Tier 3**: A trampoline class is provided for overriding the `Execution` policy with a sub-class and building your own functionality at the Python layer.

</Steps>

### Tier 1

From the top level of the `sbio` package, a `DataSource` object can be used to access the basic variant-based bindings. The `DataSource` takes a number of keyword arguments that are used to select which of the concrete specializations is desired (i.e., which of the template parameter configurations you would use, had it been C++).

The bridge to the template parameters in C++ is provided by a small set of enumerator classes on the Python side:

<Steps>

1. `sbio.FTraits`: Selects which data format to use.
2. `sbio.ExecutionPolicy`: Selects which Execution policy to use.
3. `sbio.IOPolicy`: Selects which IO policy to use (POSIX, cuFile, etc.)

</Steps>

These are provided as arguments to the initializer to select the correct specialization. From there, all objects created from the `DataSource` itself are fully detemrined, so no further specification is required.

Analogously to C++, you can still access the `Context` and use it as your entry point.

```py
import ncarray

import sbio

exp: str = "abcd"
run_num: int = 1234

ctx: sbio.Context = sbio.Context(
    epolicy=sbio.execution.ExecutionPolicy.MPI, # As above, MPIExecution.
    exec_cfg = {
        "main_rank": 0,
        "main_rank_loops": True,
    },
    # io_policy=sbio.io.IOPolicy.SyncPOSIX, # As above SyncPOSIXIO . Thats the only one available in Python right now
)

# Double check all is well in the setup so far.
if not ctx.ok():
    raise RuntimeError(f"The Context encountered errors: {ctx.error()}")

# Can query and set environment:
if ctx.has_env(key="BAD_MODE"):
    raise RuntimeError("BAD_MODE mode unsupported!)

# Construct our DataSource for XTC2 now.
# - The main difference vs C++ is that the StreamConfig is passed directly
#   as kwargs to the DataSource initializer/or Context method. Likewise, the
#   the selection of data format is done via kwarg.
# - The choice of Locator is done via different signatures with different kwargs.

ds: sbio.DataSource = ctx.data_source(
    exp=exp,
    run=run_num,
    events_per_read=43200,      # How many step offsets will be read each time.
    max_dgram_size=0x4000000,   # The maximum buffer size to read data into.
    data_fmt=sbio.FTraits.XTC2, # Data format - not all formats have the same signature
)

# Could instead use the single-file locator
# ds: sbio.DataSource = ctx.data_source(
#     path=file_path,
#     index_batch_size=43200,      # How many step offsets will be read each time.
#     max_buffer_size=0x4000000,   # The maximum buffer size to read data into.
#     data_fmt=sbio.FTraits.CXI,   # Data format - not all formats have the same signature
# )

# The Discovery step is handled in the initializer, when using Python.

# So, finally, we can go straight to a BrokerGroup and iterate!
grp: sbio.BrokerGroupWrapper = ds.group("MyDetectorName")

# Can use the simplest iteration - 1 step at a time
for step in ds.steps():
    # Pass the step, and the data request
    # The numebr of arguments for the data request must match the data format
    # - Two for XTC2, one for XTC1 and CXI
    data: ncarray.SOArrayView = grp.get_data(step, "raw", "raw")
```

### Tier 3

Finally, it is possible to extend the current implementations with functionality developed on the Python side.

Within the `sbio.core._core` module, a number of trampoline classes have been constructed from the existing C++ Execution policies. These allow overriding the implementations of the major Execution policy hooks (`should_index`, `should_process`, `next`, `pre_update`, `post_update`, `get_data`, etc.). E.g.

```py

class MyMPIExecutionPolicy(sbio.core._core.PyMPIExecution):
    def next(cls): ...

```

A full description of how to implement the overrides is beyond the scope of this brief introduction. The intent is just to highlight the possibility should it be needed.

Since the Execution policy is used as a template parameter for the other objects in the sbio infrastructure, bindings are provided for all of these using the underlying class that implements the trampoline as the template paramter. The Execution policy must be implemented first and then instantiated. While the instantiation remains in scope, the rest of the objects can then be created and will use the overrides that have been added. If an override for a particular function is not provided, then the bindings class will fallback to the parent Execution policy's implementation.

<Aside type="note" title="Overriding Other Classes">
  Currently, only the Execution policy is overrdiable. Furthermore, it must be derived from one of the existing Execution policies to start with. This is due to the way the storage allocation machinery works - providing a mechanism to allocate the `Storage` classes from Python in a robust way is quite challenging. Likewise, overriding the other classes (e.g., the data format specifications, or the StreamBrokers) has limited benefit versus just implementing it in Python from the start.
</Aside>
